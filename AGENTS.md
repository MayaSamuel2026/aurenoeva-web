This is a source-repository instruction for anyone (including AI-assisted development chats) working on this project.

**Owner direction: permanently retire the central NOEVA CORE system, not application independence.** This overrides older CORE-first / Forgejo-first / Google Cloud-first design plans and unfinished central release-controller requirements.

Canonical decision: https://github.com/MayaSamuel2026/noeva-systems-web/issues/204
Programme master: https://github.com/MayaSamuel2026/noeva-systems-web/blob/main/docs/NOEVA_SIMPLIFICATION_CANONICAL_MASTER.md

- Build, maintain, test and deploy each application independently. Never block VANTAGE or another app merely because CORE, its signing hierarchy, a release registry, Forgejo, or Google Cloud is unfinished.
- Preferred stack: ChatGPT for assisted engineering, GitHub Free for useful source control and automation, Hostinger for hosting; no new paid service without approval. No replacement CORE 2.0 platform or mandatory centralized bureaucracy.
- Retain and relocate valuable technology/code, customer records, employee identity, application configuration, contacts, historical research and existing datasets. Avoid unnecessary new repositories and duplicate workflows.
- Before live technical changes, establish a verified current known-good baseline, a usable independent recovery copy and a tested rollback route. Keep least-privilege authentication, privacy, functional checks and proportionate automated tests. Do not overwrite newer CRM/customer records by rolling back code.
- Existing production dependencies must be mapped and migrated before stopping a live service, deleting credentials, archiving shared code or removing production data. A textual CORE reference is not proof that a production process still depends on it.
- A green source-only test, GitHub PR, staging mock or release request is not a live deployment. Claim production success only on verified actual functionality and recoverability.
- GitHub baseline source snapshot: `recovery/pre-core-retirement-20261015`. This Git ref is **not** a substitute for a independently restorable Hostinger/database backup.

**Repository-specific preservation:** Preserve the current qualified website and Hostinger publish branch. The existing .github/workflows/publish.yml still assembles a historic CORE bridge: replace that bridge with an independent tested site-owned adapter before turning off the relevant service.

## Global GitHub + Hostinger execution standard — 18 October 2026 (owner directive)

**Scope:** Mandatory default for this repository and every existing and future NOEVA project, including VANTAGE, JetOceanic, AEGIS, pharma, websites, automation and research. This is an engineering instruction, **not a new approval gate, central runtime, CI controller or paid service**.

1. **GitHub Free is for source and release coordination.** Keep the existing repositories, source history, focused PR checks and proven project-owned release workflows. **Do not create a separate GitHub Actions workflow for each small feature, fix, diagnostic, test, release attempt, or one-time task.** First reuse or extend the existing project workflow or a simple script. Create a new workflow only when no suitable project-owned entrypoint exists and a distinct essential function demonstrably requires one; keep it narrow and reusable. Do not create duplicate publishers or new central orchestrators.
2. **Limit chargeable execution to useful work.** Scope CI with precise changed-file filters and the minimum relevant syntax, unit, integration and deployment checks. Avoid running the same full suite in multiple workflows or on both feature push and PR for one change. Cancel superseded **PR-only qualification** runs where appropriate; do **not** cancel, skip or auto-replace production releases, backups, or essential checks. Historical or superseded workflows may remain callable manually without automatic triggers.
3. **Hostinger owns unattended recurring execution.** Scheduled crawlers, enrichment, reports, monitoring, queues, refreshes and recurring jobs run directly on the existing Hostinger VPS with native `systemd` services/timers or `cron` as appropriate. Prefer a small app-owned script, a lock against overlaps, bounded retries, useful logs and a visible last-run result. GitHub Actions is not the standing scheduler; a self-hosted Actions runner can be a temporary transition, not a new platform.
4. **Every application stays autonomous.** Each project owns its runtime, schedule, data, deployment and recovery. Shared VPS infrastructure is acceptable; a new shared CORE, Forgejo gate, central database, custom GitHub clone, command broker or mandatory cross-project service is not. Reuse ChatGPT assistance, the connected GitHub account, the existing Hostinger subscription, and free/open technologies. Do not add optional paid tools or external AI API billing by default; ChatGPT Plus does not include separate API usage.
5. **Preserve delivery and recoverability.** Do not deactivate a current workflow, runner, timer, secret, repository, deployment, or working production route before its replacement is functioning and verified. Freeze affected current production code, retain an independent usable backup and rollback path, and prove real readback/functionality after live changes. Avoid prolonged analysis or unnecessary owner-approval loops: diagnose failures, apply the simplest working alternative and complete the approved task.
6. **No GitHub billing interruption to finish projects.** Reduce waste, but do **not** introduce a hard GitHub Actions spending cap, block billable execution, disable billing, or suspend releases as a cost measure. The owner prioritizes completing ongoing projects and accepts needed GitHub usage while waste is removed. Usage/cost reporting may inform optimization, not become another release gate.
7. **New-project default:** Begin with project source, a short project-specific `AGENTS.md` inheriting this standard, and the nearest existing project CI/release path. Do not mint a workflow, new repository, new recurring cloud job, or new infrastructure layer merely for convenience. A genuinely independent product may need its own repository; that is a source-ownership decision, not a central execution dependency.

**Operational shorthand: GitHub = code and releases; Hostinger = execution and scheduling; applications = independent.** Keep this policy practical and minimally restrictive. Later explicit owner direction for a particular task takes precedence.

## Owner-wide standing engineering rule — no patchwork in any project or process (2 November 2026)

**Applies to every NOEVA project, website, service, crawler, database/data pipeline, interface, graphic, deployment, test workflow and future engineering task. Owner's explicit instruction: NO MORE PATCHES OR PATCH-ON-PATCH WORKAROUNDS.**

- **Diagnose the actual defect first** (faulty source, component, contract, data transformation, asset, dependency or configuration). A successful build, test, publication receipt or HTTP response is not evidence that the user's observed defect is fixed.
- **Remove the defective implementation from the active path before replacing it.** Delete obsolete or conflicting code, CSS overrides, JS substitutions, visual overlays, duplicated processes, dead adapters and failed workaround layers. Preserve essential original records, migrations/audit history, approved designs, source-control history and reversible production backups; do not destructively discard real user/business data.
- **Implement one clean, canonical solution in the established system.** Prefer replacing or re-engineering the faulty component, data pipeline or interface contract over new helper layers, temporary shims, exception chains, competing systems or clever patch logic. A simple direct correction is welcome when it actually removes the defect instead of hiding it.
- **Inspect the real outcome where it matters.** Render mobile and desktop pages and inspect graphics for sharp edges, natural composition, transparency and correct layout; check authenticated business workflows, persisted data, crawled results and actual release readback where relevant. Perform focused tests, not a new bureaucracy or approval scheme.
- **Prevent regressions.** Keep the owner's full approved functionality, international ambition, working assets and integrations intact. Do not quietly narrow scope to make a defect disappear.
- **Repeated failure means discard the failed approach.** Stop retrying and layering patches; identify the root cause and re-engineer the affected component using existing infrastructure.
- **Communicate completion precisely.** Distinguish code changed, tested, deployed and confirmed working in the live product. Never count workaround additions or passing CI as finished work.

**Operational definition:** "No patches" prohibits accumulating corrective workaround layers or leaving known-broken implementations in service. It does not prohibit necessary routine security/dependency updates, direct source-code bug fixes, emergency containment to protect live data, or reversible rollout safeguards; those should still resolve the underlying cause as promptly as possible rather than become permanent patchwork.

**Goal:** Solve the original problem once, remove defective paths, verify the actual result, avoid regression, conserve time, and keep progress substantive. Do not introduce extra frameworks, delays, approvals or verification gates simply to administer this rule.

## NON-NEGOTIABLE GLOBAL ENGINEERING DEFAULT — unrestricted progress and self-repair (2 November 2026)

**Build for the complete approved business objective, not for a small arbitrary processing quota.** No permanent first-N records, first-N pages, first-N cases, countries, suppliers, products, search results, customers, or historical records. Never silently truncate scope or call an incomplete sweep "complete." Temporary per-execution budgets, rate limits, timeouts, and batches must use durable cursors/queues and resume automatically until the entire applicable workload is assessed. They are resource safeguards, **not product limits**. Scale through incremental execution, fairness, efficient persistence, and capacity management rather than by reducing the objective.

**Every unattended or recurring system must close its own recovery loop** using the app's existing scheduler/worker and authoritative data, without creating a competing central agent:
1. Persist the exact work item, evidence, state, attempt, timestamps, last verified success, and resumable checkpoint before acknowledging completion. Never equate data discovered with stock, price, licensed supply, email delivered, or commercial success.
2. Detect stalled/missed runs, stale source updates, partial publication, unresolved retries, failed deliveries/returns, and silently empty output. Report source-specific degradation and pending backlog; a cron execution or green CI is not business success.
3. Automatically retry transient errors with respectful provider-aware backoff, resume interrupted work, use an existing approved alternative source when possible, and reconcile incoming evidence. A failure must not permanently starve later items. Locking must prevent overlap without leaving permanently stuck work.
4. Verify recovery against the authoritative readback (database/website/mailbox/workflow) and close the incident only after it genuinely succeeds. Keep original evidence and data intact, correct failures at root cause, retire broken implementations instead of layering patches.
5. Escalate non-recoverable issues with precise cause, last verified state, affected work and next action. Do **not** autonomously make unsupported legal/clinical judgments, send duplicate RFQs, bypass access/security/robots or provider limits, spend money, rotate credentials, or rewrite/deploy untested production code.

**Reliability requirement:** 100% accounting for pending, attempted, succeeded, deferred and failed work; honest freshness and provenance for every daily report. External websites, mail and providers cannot be guaranteed 100% available. Work is considered implemented only when checked in; tested only with passing tests; deployed only after actual publication; recovered only after confirmed live readback. No extra approvals or architecture programmes merely to apply this rule.

Apply this rule to all existing components and all future projects. Existing app-specific legal, safety, authorization, privacy and data-integrity protections remain. An old instruction permitting an arbitrary cap, false-green status, or indefinite stall is superseded by this rule; do not revive retired NOEVA CORE.
